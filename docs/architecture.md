# SkillSprint: корневой микрофронтенд и нанофронтенды

Дата обновления: 6 октября 2026 года.

Этот документ фиксирует архитектуру, согласованную в обсуждении. Загрузчик
нанофронтендов, получение Git-исходников и формирование общего артефакта
реализованы в корне; источники четырёх бизнес-нано пока не заданы.
Доступ к настоящему стенду и его команда деплоя ещё не получены. Контракт v1
описан Zod-схемами в `packages/contracts/src/schemas.ts`; TypeScript-типы
выводятся в `types.ts`, а `index.ts` сохраняет публичные экспорты. Примеры
версий, адресов и названий пакетов иллюстрируют целевую схему.

## Что решили

- На стенде публикуется один корневой микрофронтенд SkillSprint.
- Каждый участник команды разрабатывает свой функциональный нанофронтенд.
- Исходники будут храниться в пяти репозиториях: один для корня и четыре для нанос.
  Каждый нано разрабатывается, проверяется и собирается отдельно.
- SkillSprint содержит общую оболочку и внутренний загрузчик нанофронтендов.
- Нанофронтенды могут использовать разные фреймворки и сборщики: например,
  React + Vite, Vue + Vite или React + Webpack.
- Для Vue-нанофронтендов выбран Vue 3 + Vite. Nuxt не используется.
  Они подключаются как модули через общий контракт `mount` / `unmount`.
- Целевая сборка корневого микрофронтенда — Vite вместо Webpack. Миграция
  запланирована, но пока не выполняется; совместимость с BroJS нужно проверить.
- Совместимость обеспечивается общим контрактом подключения, а не одинаковым
  стеком всех участников.
- В выбранном варианте корень и сборки нанофронтендов входят в один общий
  артефакт и публикуются вместе.
- Версии корня, отдельных нанофронтендов и контракта учитываются отдельно.
- Версии подключаемых нанофронтендов фиксируются явно; автоматический выбор
  `latest` при открытии приложения не используется.
- Выбран один поддомен для общего выпуска. Его фактический адрес пока неизвестен.

## Как работает подключение

```text
Стенд BroJS
└── fire.app стенда
    └── SkillSprint 1.3.0
        ├── общая оболочка: меню, маршруты, контейнеры
        └── внутренний загрузчик нанофронтендов
            ├── learning-plan 1.2.0 — React
            ├── trainer       2.4.1 — Vue
            └── interview     1.0.3 — React
```

У системы две границы подключения:

1. **Стенд → SkillSprint.** Корневой микрофронтенд сохраняет формат сборки,
   экспорты и жизненный цикл, ожидаемые внешним BroJS.
2. **SkillSprint → нанофронтенд.** Внутренний загрузчик использует наш общий
   контракт и передаёт модулю DOM-контейнер и контекст.

Стенду не требуется знать, на каком фреймворке написаны внутренние разделы.

## Роль второго fire.app

Под «вторым fire.app» понимается внутренний runtime проекта. Рабочее название
его пакета — `nano-runtime`. Он отвечает за реестр модулей, выбор версий,
загрузку ресурсов, подключение и отключение нанофронтендов.

Начальная стратегия — сохранить внешний fire.app стенда и реализовать
внутренний загрузчик в SkillSprint. Необходимость изменения внешнего fire.app
может появиться только после проверки ограничений настоящего стенда.

Нельзя просто запустить второй неизменённый экземпляр установленного fire.app:
его использование общего `#app`, навигации браузера и глобального контекста
SystemJS может конфликтовать с внешней оболочкой.

Внутренний runtime должен:

- работать в контейнерах, принадлежащих SkillSprint;
- иметь собственный реестр нанофронтендов;
- согласовывать навигацию с корнем;
- показывать состояния загрузки и ошибки конкретного раздела;
- освобождать ресурсы модулей при их отключении и при отключении всего корня.

## Контракт нанофронтенда

Ниже — исходная форма контракта v1 для иллюстрации. Это наш интерфейс,
а не встроенный API BroJS. Реализация находится в `packages/contracts/src`:
`schemas.ts` → `types.ts` (`z.infer`), проверки — `validation.ts`.
Внешний адаптер корня под BroJS остаётся отдельным.

```ts
export interface NanoContext {
  basePath: string
  apiBaseUrl: string
  user: { id: string; displayName: string } | null
  navigate: (path: string) => void
}

export interface NanoInstance {
  unmount(): void | Promise<void>
}

export interface NanoModule {
  contractVersion: 1
  mount(
    element: HTMLElement,
    context: NanoContext,
  ): NanoInstance | Promise<NanoInstance>
}
```

Загрузчик проверяет версию контракта и наличие экспортов во время выполнения.
Общие TypeScript-типы помогают разработке, но не заменяют runtime-проверку.

React-адаптер внутри `mount` создаёт React-root, Vue-адаптер — Vue-приложение.
Оба возвращают экземпляр с `unmount`. Корень не передаёт React-компоненты или
Vue-компоненты через общий контракт.

При переходе загрузчик отключает текущий экземпляр, подготавливает контейнер
и подключает следующий модуль. Если пользователь ушёл со страницы во время
асинхронной загрузки или подключения, устаревший результат не должен
возвращать модуль на экран; уже созданный экземпляр необходимо отключить.

## Правила взаимодействия

- Нанофронтенд управляет DOM только внутри переданного контейнера.
- Корень управляет переходами между разделами; нанофронтенд получает свой
  `basePath`. Детали вложенной маршрутизации закрепляются в контракте.
- Нанофронтенды не импортируют внутренние файлы друг друга.
- Состояние хранится внутри каждого модуля. Общий Redux-store для разных
  нанофронтендов не является частью архитектуры.
- Общие данные передаются через контекст, API и согласованные события.
  Названия событий, payload и правила совместимости описываются в contracts.
- Общий API-клиент и бизнес-типы не зависят от React или Vue.
- Дизайн-токены могут быть общими. Все новые UI-модули используют CSS-in-JS
  через Goober; Chakra UI и Emotion не используются.
- Стили описываются рядом с компонентом в `styles.ts`. Они привязаны к
  контейнеру модуля, очищаются при unmount и не используют глобальный reset.
- `unmount` освобождает таймеры, подписки, SSE/WebSocket, обработчики событий
  и другие ресурсы, созданные модулем.

## Версионирование

| Версия               | Назначение                                  |
| -------------------- | ------------------------------------------- |
| `SkillSprint 1.3.0`  | Версия общего опубликованного артефакта     |
| `trainer 2.4.1`      | Версия реализации конкретного нанофронтенда |
| `contractVersion: 1` | Версия интерфейса подключения нанофронтенда |
| `schemaVersion: 1`   | Версия структуры реестра модулей            |

Версии реализаций не обязаны совпадать. Загрузчик должен явно поддерживать
версию контракта каждого подключаемого модуля. Несовместимый контракт
отклоняется до вызова `mount` с понятным сообщением об ошибке.

Реестр фиксирует конкретный состав выпуска:

```json
{
  "schemaVersion": 1,
  "nanos": {
    "trainer": {
      "version": "2.4.1",
      "contractVersion": 1,
      "entry": "./nanos/trainer/2.4.1/index.js",
      "styles": ["./nanos/trainer/2.4.1/style.css"]
    },
    "learning-plan": {
      "version": "1.2.0",
      "contractVersion": 1,
      "entry": "./nanos/learning-plan/1.2.0/index.js",
      "styles": []
    }
  }
}
```

Адреса `entry` и `styles` разрешаются относительно URL реестра. Отдельно
нужно проверить пути дополнительных JS-чанков, шрифтов и изображений.
Поле `contractVersion` в реестре должно соответствовать экспорту модуля.

Опубликованная версия модуля не перезаписывается другим содержимым.
Несколько версий можно включить в общий артефакт, если это нужно для выбора
или отката. По умолчанию достаточно версии, выбранной для данного выпуска.

## Сборка и публикация одного микрофронтенда

Один артефакт может содержать несколько отдельно собранных модулей:

```text
артефакт SkillSprint 1.3.0/
├── index.js
├── nanos.json
└── nanos/
    ├── trainer/
    │   └── 2.4.1/
    │       ├── index.js
    │       └── style.css
    └── learning-plan/
        └── 1.2.0/
            └── index.js
```

Расположение показано логически. Фактический public URL определяется
правилами публикации стенда.

Общий процесс выпуска должен собрать корень, получить сборки конкретных
версий нанофронтендов из их отдельных репозиториев, объединить результаты
в итоговый каталог и сформировать реестр. Источник каждой сборки фиксируется
тегом или commit SHA; выбор меняющейся ветки или `latest` не используется.
Текущая реализация получает Git-исходники на фиксированных refs и собирает
каждый нано отдельно. Это настраивается в `config/nano-sources.json`.
В будущем готовые сборки можно получать из хранилища артефактов.
Очистка выходных папок
одного сборщика не должна удалять результаты другого: сборки выполняются
в отдельных каталогах, а итоговый артефакт собирается после них.

В выбранной схеме добавление новой версии нанофронтенда требует новой общей
публикации SkillSprint. Самостоятельное версионирование модулей не означает
самостоятельного деплоя.

Независимая публикация нанофронтендов и внешний изменяемый реестр — возможное
будущее расширение, но не текущий выбранный вариант.

## Разные сборщики и Vite

Планируется перевести корневой микрофронтенд с Webpack на Vite, сохранив
внешний контракт BroJS. Сейчас проект по-прежнему использует существующую
Webpack-сборку; переход ещё не реализован.

Нанофронтенды могут собираться Vite в режиме библиотеки с ESM-экспортами.
Для Vue-нанофронтендов используется Vue 3 с официальным плагином
`@vitejs/plugin-vue`; адаптер создаёт Vue-приложение в переданном контейнере
и отключает его через `app.unmount()` при вызове контракта очистки.
Внутренний загрузчик использует нативный динамический `import()`; сборка
корня должна сохранять загрузку по URL во время выполнения, а не включать
нанофронтенды в свой bundle.

Внешняя загрузка корня через SystemJS и внутренняя загрузка ESM — разные
механизмы. ESM-сборку нельзя без проверки передавать внешнему загрузчику
вместо текущей сборки BroJS.

Поле `styles` в контракте реестра v1 сохранено для совместимости. Для модулей
с CSS-in-JS оно обычно пустое: модуль создаёт и удаляет свои стили сам.
Если артефакт содержит отдельные CSS-ресурсы, загрузчик читает их из реестра. Одинаковый формат экспортов,
доступные зависимости и правильные пути ресурсов обязательны для любого
выбранного сборщика. Для начала фреймворк можно включать в собственную сборку
нанофронтенда; совместное использование React/Vue требует отдельной настройки.

`bro.config.js` является конфигурацией. В установленном BroJS CLI читает её
и вызывает Webpack. Сам по себе запуск `node bro.config.js` приложение не
собирает. Нужно установить фактическую команду CI стенда и доступный способ
подключения общего процесса сборки.

## Запланированная задача: перевести корень на Vite

Статус: задача зафиксирована, реализация отложена по просьбе пользователя.
До отдельного указания не устанавливать зависимости, не менять scripts,
конфигурацию сборки, исходники и внешний fire.app ради этой миграции.

Цель — собирать корневой SkillSprint через Vite и подключать результат
на существующем стенде как один микрофронтенд BroJS.

При реализации необходимо:

1. Уточнить команду CI стенда и требования к публикуемому артефакту.
   Изменения npm scripts не заменяют фиксированный вызов `brojs build`,
   если стенд использует именно его.
2. Настроить Vite-сборку корня с форматом и экспортами, совместимыми с
   настоящим загрузчиком SystemJS/fire.app. Обычная ESM-сборка SPA не
   считается автоматически совместимой.
3. Сохранить внешний жизненный цикл `mount` / `unmount` и ожидаемую структуру
   `default`-экспорта. Проверить отключение и повторное подключение.
4. Сохранить точку входа `index.js` и версионные пути ресурсов либо явно
   согласовать изменения с контрактом стенда. Проверить CSS, чанки и изображения.
5. Сохранить чтение конфигурации, навигации и features, предоставляемых BroJS.
   `bro.config.js` остаётся источником настроек интеграции, пока не принято
   отдельное решение об изменении этого контракта.
6. Перевести локальный запуск на Vite с работающими API-обработчиками,
   маршрутами и обновлением интерфейса. Webpack-specific HMR заменить
   подходящим механизмом Vite.
7. Проверить необходимость Babel в выбранной конфигурации. Не переносить
   существующие Babel presets автоматически; проверку TypeScript-типов
   организовать отдельно от преобразования исходников.
8. Проверить сборку и подключение в локальной оболочке с существующим fire.app,
   затем на настоящем стенде. Отдельно проверить будущую загрузку ESM-нанофронтендов.

Миграция считается подтверждённой после успешной сборки и проверки подключения,
ресурсов, навигации и жизненного цикла. Если доступен только локальный стенд,
совместимость с внешним стендом остаётся неподтверждённой и это нужно явно указать.
Изменение общего fire.app не является обязательной частью задачи: необходимость
такого изменения должна следовать из конкретного выявленного ограничения.

## Репозитории и независимая разработка

Все пять репозиториев относятся к одному проекту SkillSprint в Bitbucket:

```text
SkillSprint (проект Bitbucket)
├── skillsprint                # корневая оболочка, BroJS, загрузчик, контракты
├── skillsprint-learning-plan   # нанофронтенд плана подготовки
├── skillsprint-trainer         # нанофронтенд тренажёра
├── skillsprint-interview       # нанофронтенд AI-собеседования
└── skillsprint-progress        # нанофронтенд прогресса
```

Названия четырёх репозиториев нанос — выбранные ориентиры для создания;
их наличие в Bitbucket этим документом не подтверждается.

Каждый нанофронтенд должен иметь собственные `package.json`, lock-файл,
зависимости, точку входа, команды запуска, проверки и сборки, а также CI.
Локальная страница модуля вызывает его `mount` с тестовым контекстом и позволяет
работать без запуска корня или других нанос. Корень проверяет совместную работу.

Подключение нано выполняется по URL собранного модуля из реестра через контракт
v1. Импорт исходников из соседнего репозитория и включение нано в bundle корня
не используются. Для локальной интеграции реестр может указывать адрес
dev-сервера нано; сервер должен отдавать совместимый модуль и разрешать доступ
с origin корневого приложения.

Источник общих контрактов остаётся в `packages/contracts` корневого репозитория,
с сохранением публичных экспортов v1. Для использования другими репозиториями
подготовлен пакет `@skillsprint/contracts@1.0.0`, собираемый и упаковываемый
командами корня. Способ его распространения между репозиториями ещё нужно
согласовать. Нано фиксируют версию пакета; отдельные копии схем не создаются.
Шестой репозиторий сейчас не требуется. Пакет во внешний реестр не опубликован.

Разделение репозиториев обеспечивает отдельную разработку и сборку. На стенд
по-прежнему публикуется один общий артефакт; независимый деплой нанос остаётся
будущим расширением. Прежняя общая workspace-структура `apps/*` больше не является
целевым размещением четырёх нанос.

Текущий корень остаётся в этой папке: `src/app`, `src/pages`, `src/shared`, API
в `server/api`. Загрузчик находится в `packages/nano-runtime`, контейнер React —
в `src/pages/nano`, команды выпуска — в `scripts/release`. Конфигурация содержит
четыре записи с `source: null`; полный выпуск запрещён до задания Git-источников
всех четырёх модулей. Демонстрационные модули удалены; подключаются только
сборки из настроенных источников. Инструкция — `integration.md`.
Актуальное дерево и правила размещения файлов описаны в `structure.md`.

## Что проверить до реализации всей системы

1. Фактическую команду сборки на стенде и возможность добавить сборку нанос.
2. Какие каталоги входят в публикуемый артефакт и доступны ли вложенные JS/CSS.
3. Внешний контракт настоящего fire.app: экспорты, форматы, маршруты и отключение.
4. Минимальную связку: стенд → SkillSprint → React-нано и Vue-нано.
5. Загрузку CSS, чанков и изображений по версионным адресам.
6. Переходы, повторное подключение, ошибки и очистку при отключении корня.
7. Выбор двух опубликованных версий одного нано и отказ при несовместимом контракте.

Документ фиксирует решение и ориентиры реализации; он не подтверждает
совместимость со стендом и не является поручением автоматически переписывать
fire.app, сборку или текущие исходники.
